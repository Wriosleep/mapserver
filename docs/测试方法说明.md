## 一、被测对象:一条"每个环节都不敢报错"的链路

先说清楚这条链路长什么样,以及**错在哪里最难被发现**。

| 环节 | 产物 | 可观测面 | 典型的静默失败 |
|---|---|---|---|
| ① 下载 | `tiles_xyz/{z}/{x}/{y}.png` | 文件是否存在、是不是真瓦片 | 服务端返回 200 + 一页 HTML 错误页,被当成下载成功 |
| ② 切片 | 同上(由源图切出) | 数量 4^z、尺寸 256×256、命名规范 | 源瓦片缺失时安静地少切,不报数 |
| ③ 翻转 | `tiles_tms/{z}/{x}/{y}.png` | 内容与 XYZ 逐张交叉对应 | Y 轴没翻(或 X、Y 都翻了),页面照样能打开 |
| ④ 托管 | HTTP 响应 | 状态码、响应头、响应字节 | SELinux 拦截返回 403、防火墙没放行、被别的东西占了端口 |
| ⑤ 渲染 | 浏览器页面 | 左右两张图是否一致 | 底图颠倒,但标记点还在,人眼要盯着看才发现 |

**这条链路的核心特征是"全都不报错"。**

下载到假瓦片、源瓦片少了几张、Y 轴忘了翻——这些情况里,**脚本都会正常退出,产出 1365 个文件,浏览器也能把页面打开**。看上去一切正常。

所以本项目的测试设计只有一个出发点:

> 在每个"系统会安静地骗你"的地方,埋一个机器能判的断言。

这句话决定了下文所有的取舍。

## 二、分层:四层,按"运行成本 × 外部依赖"切

```
L0 单元   test_unit.py         43 条   纯函数,不碰磁盘        毫秒级
L1 集成   test_integration.py  12 条   读写磁盘产物,子进程    秒级
L2 接口   test_api.py          16 条   HTTP,依赖 VM 上的 Apache  依赖环境
缺陷回归  test_defects.py       2 条   复现已知缺陷,固定为 xfail
────────────────────────────────────────────────────────────
L3 系统   手工清单             8 条   部署链路(SELinux / 防火墙)
L4 性能   ab / wrk             7 条   并发容量
L5 前端   Playwright           7 条   渲染层
```

**73 条是 pytest 展开参数化之后的数量,不是函数个数。** 例如 U-01 一个函数挂了 5 个 z 值,算 5 条。对外说"73 条"时要能立刻补充这句,否则会被追问对不上。

### 分层依据

切层的依据不是"代码目录",而是两个维度:**运行一次要多久**、**依赖多少外部东西**。

三条原则:

1. **能在下层测的,绝不推到上层。** 翻转公式是个纯函数,用 `f(f(y)) == y` 就能验完,不需要真的产生 1365 个文件,更不需要开服务器。L0 只有 43 条,但锁死了算法本身。
2. **越依赖环境,越靠后。** L2 需要虚拟机开着、Apache 起着的,才放最后。L3/L4/L5 需要人、需要压测工具、需要浏览器,本轮不自动化。
3. **每层失败要说清楚是谁的责任。** L0 红了 = 算法错了;L1 红了 = 产物契约破了;L2 红了 = 部署或网络有问题。**如果所有用例都堆在一个文件里,失败信息就没法给出这个指向。**

### L0 与 L1 的边界

两者都可能用到磁盘,区别在于**是否验证真实产物**:

- L0 里的 `test_u10` 切片用例,在 `tmp_path` 里造一张小源图自己切,验的是"切出来的边长是不是 256"这个**函数契约**;
- L1 的 `test_i01` 读的是仓库里真实的 `tiles_xyz/`,验的是"这次交付的数据合不合约"。

前者在别人的机器上也能跑,后者要求先跑过切片脚本。混在一起,CI 就会莫名其妙红。

## 三、判据(oracle):"对"的标准从哪来

测试最容易糊弄的地方,是"预期结果"其实没人定义过。本项目每个层级的判据都有明确出处:

### 3.1 数学恒等式 → 全量交叉比对

XYZ 与 TMS 的 Y 轴翻转关系:

```
y_tms = 2^z - 1 - y

等价写法(用来做断言):
    tiles_tms / z / x / y        的内容
  ==
    tiles_xyz / z / x / (2^z-1-y) 的内容
```

**为什么用 MD5,而不是肉眼看图或像素相似度:**

- 翻转只改变**编号**和**位置**,不改变字节。所以正确实现的产物必须**逐字节完全相等**,任何"相似但不相等"都说明出了问题。
- 视觉比对需要定阈值,阈值就要有人拍脑袋,还会漏掉"某一块颜色接近但内容错了"。
- 二进制相等是**没有争议的判据**——它要么成立,要么不成立。

代价是慢一点,但 1365 张 MD5 跑完不到 3 秒。**判据硬,才能当真回归用。**

### 3.2 契约 → 数量与命名

从金字塔结构本身推出的,不需要人工指定:

- 级别 z 有 `4^z` 张 → z0~z5 合计 `(4^6-1)/3 = 1365`
- 每张严格 256×256
- 命名严格 `{z}/{x}/{y}.png`,且 `x, y ∈ [0, 2^z-1]`

这类判据的好处是**能自动发现"少了"或"多了"**,而不是只验证"现有文件看起来没问题"。

### 3.3 往返 → 投影函数

`lat → px → lat` 回到原值且误差 < 0.01°,覆盖南北半球(含悉尼 -33.87°)。

另外两条边界:纬度 ±90° 必须**截断到 ±85.05112878**(墨卡托的极点极限),而不是产生 `inf` 或 `nan`——后者会让切片程序崩在半夜三点。

### 3.4 反例 → 负向与安全

正向用例证明"该成的成了",负向用例证明"不该成的没成"。后者在瓦片服务上尤其要紧:

| 反例 | 判据 |
|---|---|
| 请求不存在的级别 `9/0/0.png` | 404,不能是 200 |
| 路径穿越(`../etc/passwd` 等 4 种编码变体) | 不得 200,且响应体不含 `root:` |
| 大写扩展名 `0/0/0.PNG` | 404(Linux 文件系统区分大小写) |
| 源瓦片只有 3/4 张 | 计数如实回 3,**不许被掩盖成"处理完成"** |

最后一条是负向里最容易被忽略的:**测试不只要验"结果对不对",也要验"出错时敢不敢说出来"**。

### 3.5 幂等 → 确定性

同一份输入,`convert_tiles.py` 跑两次,产物必须**逐张 MD5 一致**。转换是纯函数式操作,不该有随机性;一旦不一致,说明某处引入了时间戳、浮点误差或并发竞争。

### 3.6 「200 不是判据」

这是本项目最容易踩的坑,单独列一节。

部署验证时,如果只看状态码,下面三种情况**都会返回 200**:

1. SELinux 拦了,但被别的虚拟主机接住,返回了默认欢迎页;
2. 端口被 nginx / 别的服务占着,Apache 根本没起来;
3. 反向代理缓存了一份旧响应。

所以 L2 的 A-03~A-07 分别查:

| 查什么 | 为什么 |
|---|---|
| `Server` 头含 `Apache/2.4.63 (CentOS Stream)` | 确认搭话的确实是目标服务 |
| `Content-Type: image/png` | 确认返回的是图,不是 HTML |
| `Content-Length` == 实际响应长度 | 确认没被截断/没被压缩改写 |
| 响应体前 8 字节 == PNG 魔数 | 确认**内容是图片**,不是伪装成 png 的错误页 |
| 响应体 MD5 == 本地 `tiles_tms` 同路径文件 | 端到端逐字节保真 |
| `HEAD` 与 `GET` 的状态码和长度一致 | 确认头部可信 |

**状态码是服务端最愿意撒谎的信号。** 承认这一点,是接口测试和"用 curl 点一下"的分水岭。

## 四、覆盖度:从 2 张到 1365 张

### 起点

项目自带的 `convert_tiles.py::verify_flip()` 会做翻转自检,但**只抽查 z=1 的两张瓦片**(`1/0/0` 与 `1/0/1`)。

它打印 `-> 通过`,人看一眼就过去了。

### 为什么这不够

1. **抽样比例 2/1365 ≈ 0.15%,且样本集中在最低层级。** z=5 的 1024 张里,翻转公式只要在高位出现进位错误(比如 `2^z-1-y` 写成了 `2^z-y`),抽样永远发现不了。
2. **打印出来的结果不是断言。** 人眼扫过 `[OK]` 就翻页了,某天真的错了,也没人会回头比对。
3. **无法回归。** 改了代码之后,没有人会重新手工核对 1365 张。

### 做法

把同一个判据作用到全量:

```python
for z in levels:                    # z = 0..5
    n = 2 ** z
    for x in range(n):
        for y in range(n):
            assert md5(tms/z/x/(n-1-y)) == md5(xyz/z/x/y)   # 逐张
```

结果:**1365/1365 全部一致**。覆盖度从 2 张提升到 1365 张,**682 倍**。

### 再加一道:防止"整体反转"的假成功

如果有人把 X 轴也一起翻了(比如误写成对整条路径做镜像),逐张比对会立刻发现。但如果有人把 `tiles_tms` 整个目录**倒序重排**,某些实现也能"碰巧"通过内容比对。

所以 I-04 单独查一层:**z 级下的 x 列目录集合必须原样保留**,只有 y 变了。

> 覆盖度不只是"测了多少条用例",更是"一条判据作用在多少数据上"。前者可以靠参数化注水,后者不能。
>
> 另外,`test_i10` 会去 README 里核对"1365"这个数字。**文档里的数字本身也是被测对象**——它一旦过期,后面所有基于它的判断都错。

## 五、隔离:测试不能污染被测物,也不能被环境绑架

### 5.1 造数据用临时目录

所有"需要修改产物"的用例(`--clean` 清理、JPG 转换、RGBA 剥离、源瓦片缺失),都在 `tmp_path` 里搭一个微型金字塔(比如只有 z0~z1 共 5 张),跑完自动删除。

真实产物只读不写。这样:

- 本地跑测试不会把数据集搞脏;
- 同一个用例可以在任意目录反复跑;
- 失败时容易复现,因为输入是测试自己造的。

### 5.2 环境不可达时 skip,而不是 fail

L2 依赖虚拟机上的 Apache。`conftest.py` 的 `tile_server` 夹具会先 `HEAD /tiles/0/0/0.png`,连不上就整组 skip:

```python
try:
    requests.head(f"{url}/0/0/0.png", timeout=3)
except Exception as exc:
    pytest.skip(f"瓦片服务器 {url} 不可达,跳过接口测试: {exc}")
```

**理由:** 环境没开是配置问题,不是代码问题。让它 fail,每天都会产生 16 条假红灯,久而久之没人看结果——**测试套件一旦不可信,比没有还糟。**

但 skip 必须**带原因**打印出来,不能静默跳过。所以报告里 16 条 skip 要写明是"环境未就绪",而不是"未覆盖"。

地址也可以通过环境变量覆盖:

```bash
TILE_BASE_URL=http://127.0.0.1/tiles pytest tests/test_api.py
```

**skip 有两种,必须分开说。** 本项目各出现了一次,正好可以对照:

| 类型 | 例子 | 特征 | 环境修好后 |
|---|---|---|---|
| **环境未就绪** | 虚拟机没开,16 条接口用例全 skip | 用例本身可执行,只是连不上目标 | 变通过(实测 15 通过) |
| **验证条件不成立** | A-13 需要两个可达入口,从宿主机凑不出第二个 | 用例的**前提**在当前拓扑下不满足,不是"还没来得及跑" | 仍然是 skip,除非改变拓扑或在服务器本机跑 |

前一种 skip 是暂时的,后一种是永久性的——除非执行环境变。报告里如果只写"1 条 skip"而不区分,读的人就分不清是"漏测"还是"测不了"。

> 这也是为什么 A-13 的 skip 信息里必须写明"未设置 `TILE_BASE_URL_ALT`":光有一个 `s` 字母,说明不了任何事。

### 5.3 编码与字体

两个跨平台坑,都会以"测试莫名其妙变红"的形式出现:

- **控制台编码**:Windows 默认 GBK,断言信息里的中文会变乱码。`conftest.py` 启动时统一 `reconfigure(encoding="utf-8")`。
- **中文字体**:`gen_source.py` 要在源图上画地标名。Windows 用 `msyh.ttc`,Linux(CI)没有,`load_font()` 按多平台路径依次探测;CI 里显式安装 `fonts-noto-cjk`。字体缺失时会退回 PIL 默认位图字体,中文变方块——程序不崩,但**生成的源图与本地不一致**,人工对比截图时会困惑。

## 六、缺陷:怎么发现、怎么固定、怎么验收

### 6.1 发现方式

不是跑出报错,而是**对着文档和代码逐项核对**时发现的:

- 缺陷 D-01:文档说"断点续传",代码里判断"文件存在且大小 > 0"。两句话不是一回事。
- 缺陷 D-06:README 写"24 线程实测",脚本 `--workers` 默认值是 8。按文档复现得不到同样的性能数据。
- 缺陷 D-07:Apache 配置里没有任何 `Cache-Control`,而 README 的"后续工程建议"里写了这一项——说明写文档时知道,部署时漏了。

**D-06 和 D-07 属于"文档与实现不一致",这类缺陷在多数项目里根本没进缺陷单,但它们是同一类东西:说出去的和做出来的不一样。**

### 6.2 用 xfail 固定,而不是删掉

```python
@pytest.mark.xfail(reason="已知缺陷 D-01:断点续传只判文件非空,不校验内容")
def test_d01_resume_treats_corrupt_file_as_complete(tmp_path):
    ...
```

三态流转:

| 状态 | 含义 | 该做什么 |
|---|---|---|
| `xfail` | 缺陷确认存在,用例稳定复现 | 保留,等修复 |
| `XPASS` | 缺陷被修好了 | **去掉 xfail 标记** |
| 去掉标记后 PASS | 正式纳入回归 | 闭环完成 |

关键点:**xfail 用例断言的是"缺陷存在"这个事实,不是"期望的正确行为"**。所以修好之后它会自动 XPASS 提示你,而不是假装一切正常。

如果反过来写(断言期望行为 + xfail),修复之后没人会发现,用例会一直"红得理所当然"——那等于没测。

### 6.3 一个诚实的边界

这 6 个缺陷是**测试发现的,代码没有改**。原因见《项目价值》第五节:这是论文复刻项目,改动会让产物偏离论文基线。

所以对外表述是"**定位并给出修复方案**",不是"修复了缺陷"。这是同一份材料里最容易说过头的地方。

## 七、CI:让测试不依赖"本机恰好是什么状态"

`.github/workflows/tests.yml`,在 push / PR / 手动触发时执行。

```yaml
- name: Build tile artifacts          # ← 关键的一步
  run: |
    python gen_source.py
    python slice_tiles.py
    python convert_tiles.py

- name: Run tests
  run: python -m pytest -q --alluredir=allure-results
```

### 三个设计决定

**① CI 里从源图重新生成产物,不依赖仓库里的文件。**

`tiles_xyz/`、`tiles_tms/` 被 `.gitignore` 排除了(近 3000 个小文件,而且都是产物不是源码)。所以 CI 必须自己重建。

这带来一个额外的好处:**每次 CI 实际在验证"仓库里的脚本当前能不能产出合规产物"**。如果哪天有人改坏了切片逻辑,即使没人改测试,I-01/I-03 也会红。这叫"对产出过程回归",比只对存量数据回归更有意义。

**② 接口层在公开 runner 上必然 skip。**

GitHub 的公开 runner 访问不到内网虚拟机上的 Apache。所以 16 条 L2 在 CI 里**恒为 skip**。

这不是漏测,是设计——但**必须说清楚**,否则看报告的人会以为 16 条通过了。这也是本套设计里唯一一处"通过率"需要解释而非报数的地方。

**③ Allure 报告作为 artifact 保留 14 天。**

每一条用例都带 `@allure.feature / @allure.story / @allure.title`,失败时能直接看出是哪个环节、哪个用例、什么输入。

### 运行记录

**2026-10-28 推送 `9722b2b` 后,远端 GitHub Actions 运行通过。** 这是第一次真机验证,它一次性确认了三件事:

1. workflow 配置本身可用(环境、依赖、字体、步骤顺序都对);
2. **从源图重新生成的产物通过了 L1 集成测试**——说明仓库里的脚本当前确实能产出合规数据,而不是"本地碰巧有存量产物";
3. I-10 对 README 的核对也过了,说明文档里的数字与产物一致。

**同日虚拟机就绪后跑全量:`70 通过 / 1 skip / 2 xfail / 0 失败`。** 部署态(SELinux 标签、firewalld 放行、Alias 配置)由此获得实际验证,不再只靠踩坑记录背书。唯一 skip 的 A-13 属"验证条件不成立"(见 5.2),不是环境问题。

对照:

| 环境 | 结果 | 含义 |
|---|---|---|
| 虚拟机就绪 | 70 通过 / 1 skip / 2 xfail | 整条链路含部署态 |
| 虚拟机未启动 | 55 通过 / 16 skip / 2 xfail | 仅本地链路 |
| CI(公开 runner) | 55 通过 / 16 skip / 2 xfail | 恒等于上一种,访问不到内网 VM |

> **CI 绿 ≠ 73 条全过。** CI 的 55 就是"本地链路全过"的那个 55,接口层在 CI 上永远 skip。

## 八、没有测的部分

| 层级 | 项 | 原因 | 风险 |
|---|---|---|---|
| L2 | 16 条接口用例本轮 skip | 虚拟机未启动 | SELinux / 防火墙 / Alias 部署链路未经单轮回归 |
| L3 | S-01~S-08 系统测试 | 需要手工操作虚拟机 | 部署缺陷只能靠踩坑记录,不能在 CI 复现 |
| L4 | P-01~P-07 性能 | 无压测工具基线 | 无法回答"能扛多少 QPS",也不能做 httpd / nginx 对比 |
| L5 | E-01~E-07 前端 | 未接 Playwright | 三个验证点仍靠肉眼 |
| - | DEM 高程与三维 | 论文环节,本项目未实现 | 不在范围内 |

**写清楚这些,比假装全覆盖更有用。** 面试时主动说局限,比被问出来强——前者叫边界感,后者叫露馅。
