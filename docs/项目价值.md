## 二、技术价值:和论文比,多做了什么、少做了什么

| 论文环节 | 本项目做法 | 评价 |
|---|---|---|
| BIGEMAP / 水经注手工下载瓦片 | `download_tiles.py` 调在线瓦片 API,带断点续传、重试、并发 | 从"点鼠标"变成"可重复、可参数化" |
| VS2010 + Qt + OpenCV 写转换工具 | `convert_tiles.py`,193 行 Python | 算法一致,成本低一个数量级;代价是没做 GUI |
| RAID0 / DAS 直连存储 | 未做 | 1365 张只有 4.39 MB,做了没有意义。**要能说出"为什么不做"** |
| OSGEarth 三维地球 | Leaflet 1.9.4 二维 | OSG 编译成本极高;二维足以验证整条数据链路 |
| `tms.xml` 描述文件 | 未做 | Leaflet 用 `tms: true` 代替 |
| 谷歌 DEM 高程 | 未做 | 三维地形才需要 |
| **论文没有的:可回归的测试体系 + CI** | pytest 73 条 + GitHub Actions + Allure | **这是本项目相对论文的净增量** |

### 三条从数据里推出来的结论(不是抄论文的)

这类结论最有价值,因为它们是**自己算出来的**:

**1. 小文件的块分配开销**

```
实际数据量   4.39 MB(4,606,886 字节)
磁盘占用     约 7.3 MB
差额         约 66%
```

1365 个文件平均 3.30 KB,而文件系统按 4 KB 块分配——**不足一块也要占满一块**。一个 5 KB 的瓦片和一个 4 KB 的瓦片,在磁盘上一样大。

这条结论直接解释了:为什么瓦片服务普遍用 MBTiles 打包、对象存储或 SSD,而不是把几百万个小文件摊在文件系统里。

**2. 存储量外推**

按实测单片 3.30 KB 推算,z18 单级别约 **210 TB**。这就是论文说"全国地图需要百 TB 以上"的由来,也是为什么真实瓦片服务必须**金字塔 + 按需加载**——客户端只请求视野内那几十张,而不是把整库拉下来。

**3. 3 个真踩过的坑,3 条可复用的经验**

| 坑 | 教训 |
|---|---|
| 403 但 `ls -l` 权限全开 | SELinux 标签和文件权限是两套体系,`restorecon` 不能省 |
| VM 内正常,外面不通 | `firewall-cmd --permanent` 和 `--reload` 是两步,少一步等于没配 |
| 换瓦片源后全部 404 | CartoDB 是 `{z}/{x}/{y}`,Esri 是 `{z}/{y}/{x}`——**同样的概念,不同的约定** |

## 三、测试能力价值:这个项目证明了你什么

按"面试官会怎么读"来组织。每一条都给出**可验证的证据**,不是形容词。

### 1. 能自己造 oracle,而不是只回放别人写的用例

最核心的一条。绝大多数学生项目的测试是"我调用一下,看它没报错"。这个项目里,**预期结果的来源是可推导的**:

- 翻转对不对 → 数学恒等式 `tms(z,x,y) == xyz(z,x,2^z-1-y)`
- 数量对不对 → 金字塔结构 `(4^6-1)/3 = 1365`
- 投影对不对 → 往返 `lat→px→lat`,误差 < 0.01°
- 部署对不对 → 响应字节 MD5 == 本地文件 MD5

> **会写用例的人很多,能把"什么叫做对"定义清楚的人不多。** 这是这个项目最值得讲的一点。

### 2. 有覆盖度意识

项目自带的 `verify_flip()` 只抽查 z=1 的 2 张。测试把它扩到**全量 1365 张**,覆盖度提升 **682 倍**。

而且能说出"为什么抽样不够":2/1365 只有 0.15%,且样本集中在最低层级——z=5 的 1024 张里,翻转公式只要出现进位错误,抽样永远发现不了。

### 3. 会做负向与安全

只测 happy path 是新手最常见的特征。这里有:

- 404 负向(不存在的级别)
- 路径穿越 4 种编码变体
- 扩展名大小写敏感
- 源瓦片缺失时**计数要如实报出来**,不许被掩盖
- `--clean` 破坏性操作的清理验证

### 4. 分得清「通过」和「真的对」

状态码 200 是服务端最愿意撒谎的信号。所以接口层不只看 200,还查:

`Server` 头 → `Content-Type` → `Content-Length` 与实际长度 → PNG 魔数 → 响应体 MD5 → `HEAD`/`GET` 一致性

### 5. 能处理不确定的环境

虚拟机没开时,16 条接口用例**自动 skip 并打印原因**,而不是 fail。

理由:环境没就绪是配置问题,不是代码问题。让它红,每天 16 条假红灯,久而久之没人看结果——**测试套件一旦不可信,比没有还糟**。

### 6. 缺陷闭环,而不只是"发现 bug"

发现 → 确认 → 用 xfail 固定 → 修复后自动 XPASS → 摘标记转正式回归。

**xfail 断言的是"缺陷存在"这个事实**,所以修好后它会自己提醒你,而不是假装一切正常。

### 7. 工程习惯

- 产物不进版本库(`tiles_*` 近 3000 个文件),CI 里重新生成
- 测试用 `tmp_path` 造数据,不污染真实产物
- Allure 注解到每条用例,失败能定位到环节
- 文档里的数字也被测试盯着(`test_i10` 核对 README 的 1365)

### 8. 诚实

主动列出未测项:L2 环境未就绪、L3/L4/L5 全部未跑、DEM 未做。

## 四、面试口径

### 4.1 简历四条 STAR 的展开(每条 30 秒)

**① "pytest 分层 73 条用例"**

> 按"运行成本 × 外部依赖"分了四层:单元 43 条测纯函数,集成 12 条测磁盘产物契约,接口 16 条测 HTTP 语义,另外 2 条是缺陷回归。
>
> 分层的原则是能在下层测的绝不往上推——翻转公式用 `f(f(y))==y` 就能验完,不需要真产生 1365 个文件才去验。

**② "抽样校验升级为 1365 张逐张比对"**

> 项目原有的自检只抽查 z=1 的两张瓦片,抽样率 0.15%,而且打印出来是给人看的,不是断言。
>
> 我把它扩展成全量:对每个 (z,x,y),拿 `tms/z/x/(2^z-1-y)` 的 MD5 去比对 `xyz/z/x/y`,1365 张全部一致。另外单独加了一条,确认 x 列目录原样保留——防止"整体重排也能碰巧通过"。

**③ "定位 6 个缺陷并给出修复方案"**

> 最有代表性的是断点续传那个:脚本判断"已完成"的依据是文件存在且大小大于 0。但服务端限流时会返回 200 加一页 HTML,这会被当成下载成功,之后永久跳过。一次网络抖动就在数据集里埋一张假瓦片,而且全程不报错——直到有人在浏览器里看到一块空白。
>
> 修复方案是跳过之前校验 PNG 魔数。我已经用 xfail 把复现路径固定成回归用例,修好会自动转 XPASS。

**④ "GitHub Actions + Allure"**

> 瓦片产物不进版本库,所以 CI 里是从源图重新生成再跑测试。这样每次 CI 实际在验证"当前脚本还能不能产出合规产物",比只对存量数据回归更有意义。
>
> 接口层的 16 条在公开 runner 上恒为 skip,因为访问不到内网虚拟机——这一条我会主动说明,避免被理解成 16 条通过了。

### 4.2 高频追问预案

| 问题 | 答法 |
|---|---|
| **73 条里有多少真跑了?** | 55 条通过 + 16 条 skip(接口层,虚拟机未开,可一键复跑)+ 2 条 xfail(已确认缺陷)。**不说 100%** |
| 16 条 skip 是不是等于没测? | 不是。用例已就绪,只需 `TILE_BASE_URL` 指向;skip 是"环境未就绪",不是"没写" |
| MD5 逐张比对是不是太重? | 1365 张跑完不到 3 秒。而且翻转只改编号不改字节,**二进制相等是唯一没有争议的判据**;用视觉相似度需要拍阈值,反而不可靠 |
| 为什么不自动测前端? | 分层取舍。三个验证点(左右一致 / 取消 TMS 后颠倒 / 标记不随底图动)留了 Playwright 的位置,但优先级排在接口和性能之后 |
| 缺陷为什么不修? | 这是论文复刻项目,改代码会让产物偏离论文基线。所以给修复方案 + xfail 固定,而不是直接改。表述上统一说"**定位并给出修复方案**" |
| 性能测了吗? | 没测,这是本项目最大的空白。下一步用 `ab` / `wrk` 建 httpd 的 QPS 曲线,再和 nginx 对比 |
| 这个项目能改造成生产级吗? | 能,但要说清三条:① 换 MBTiles 解决小文件块开销;② 加 `Cache-Control`(现在完全没有,D-07);③ 多副本 + CDN。另外 4.39 MB 的规模离生产还差很远 |
| 为什么选这个论文? | 链路完整(下载→转换→部署→渲染四段都有)、判据明确(翻转有数学恒等式)、可离线复现(自己能生成源图) |

### 4.3 三句绝对不能说

| ❌ 不能说 | 为什么 | ✅ 改成 |
|---|---|---|
| "用例通过率 100%" | 16 skip + 2 xfail 不是通过。面试官一查 pytest 输出就穿 | "55 条本地链路全过" |
| "做了 CI/CD" | 只做了 CI,没有 CD(部署仍是手工) | "GitHub Actions 持续集成" |
| "修复了 6 个缺陷" | 代码没改 | "定位并给出修复方案" |

> 这三句是同一份材料里最容易说过头的地方。**测试岗面试官会拿数字对账**,任何一个数字对不上,会连带整页可信度。

## 五、局限(主动说,别等问)

| 局限 | 影响 |
|---|---|
| 规模小:1365 张 / 4.39 MB | 真实服务是 TB 级,不能证明大文件量下的能力 |
| 数据源是公开瓦片或合成图 | 没有真实业务数据、没有权限体系 |
| 无并发性能基线 | 回答不了"能扛多少 QPS" |
| 无前端自动化 | 渲染层三个验证点靠肉眼 |
| 无三维 / DEM 环节 | 论文的 1/4 未复刻 |
| 6 个缺陷只给方案未落地 | 缺陷闭环停在"固定"这一步 |

**主动说局限的收益:换来自证可信。** 一个能准确说出自己项目边界的人,比一个什么都说"没问题"的人可信得多。
